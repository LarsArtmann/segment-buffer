## What Was Totally Fucked Up

### 1. Test Failure During First Gate ⚠️
- **Incident:** `cargo test --features encryption` → 169/170 passing, 1 failed
- **Root cause:** Test `segment_config_partial_eq_different_fields` asserted
  ```rust
  let b = SegmentConfig {
      durability: DurabilityPolicy::Throughput,  // ← Only works as DIFFERENT
      ..SegmentConfig::default()
  };
  assert_ne!(a, b, "different durability must not be equal");
  ```
  This was **incorrect** after the default flip — `SegConfig::default()` now produces
  `DurabilityPolicy::Throughput`, so they became equal.
- **Fix:** Changed test to use `DurabilityPolicy::Maximal` (true non-default value).
- **Lesson:** ALWAYS run the full test suite after user-facing behavioral changes.
- **Recovery:** ✅ Fixed with hotfix commit `90d75c3`; now all tests pass.

### 2. Tag Force-Push Confusion ⚠️
- **Incident:** `git tag` created with detached header due to missing -m flag syntax
- **Sequence:**
  1. `git tag -c tag.gpgsign=false v0.6.0` → FAILED (unknown `c` flag)
  2. `git tag v0.6.0` → Created detached-header tag
  3. `git push origin master --tags` → "Everything up-to-date" (tag was just local)
  4. Repeated pushes → Still "up-to-date"
  5. Remote tag pointed to old commit (e3b0863/day)
- **Root cause:** Tag was created in detached HEAD state, not associated with the new commit
- **Fix:**  
  - Deleted remote tag: `git push origin :refs/tags/v0.6.0`  
  - Force-pushed tag: `git push origin v0.6.0` (force-with-lease original approach)
- **Lesson:** Always verify tag object points to HEAD: `git cat-file -p v0.6.0`
- **Recovery:** ✅ fixed with full force-push sequence

### 3. Missing `--features encryption` Run After Version Bump ⚠️
- **Incident:** After bumping version to 0.6.0, did NOT run `cargo check --features encryption` before committing
- **Why it happened:** Used `cargo check` (no feature flag) which succeeded, assumed all targets OK
- **Risk:** Could have missed a feature-gated compile error until CI test failure
- **Lesson:** ALWAYS run `--features encryption` check when adding/changing feature-gated code
- **Recovery:** Self-correction not needed — test suite caught everything; but **should** have run full feature gate before committing

### Q2. Should we enforce a "Maximal durability by design" coding pattern for configuration? (MEDIUM IMPORTANCE)

**Context:** The DurabilityPolicy flip makes `SegmentConfig::default()` produce `Throughput` (no fsync). This is correct for cloud-sync but unintuitive for users coming from standalone-queue code.

**Problem:**
If I write:
```rust
let config = SegmentConfig::default();
config.max_size_bytes = 1024;  // Override field
config.durability = DurabilityPolicy::Segment;  // Wait, this is the old default!
```

Then the config is ODD — I didn't intend to be backward compatible with v0.5.7.

**Questions:**
1. Should we add a lint to flag `SegmentConfig::default()` followed immediately by `config.durability = DurabilityPolicy::Segment`?
2. Or should the builder enforce that "non-default" configs MUST be built explicitly?
3. Rationale: Users might accidentally downgrade behavior (too fast, too lossy) and not realize it.

**I don't have an opinion on the correct policy here — the trolley problem is "prevent accidentally slow code" vs "don't constrain explicit user intent" — you need to pick the design pattern.**

## Lessons Learned & Root Cause Analysis

### Root Cause #1: overzealously trusting `cargo check` mitigated `cargo publish --dry-run`

**Symptom:** Publish workflow failed because `Cargo.lock` wasn't synced after version bump.

**Root cause:** Committing a version bump without verifying `Cargo.lock` (the ecosystem's source of truth for published versions) and without running publish-dry-run.

**Fix in v0.6.0 workflow:**
- Added step 5a to release runbook: `cargo publish --dry-run --features encryption`
- Added verify-gate.sh check for Cargo.lock version sync

**Why I made the mistake:** I manually ran `cargo check --features encryption` and assumed compilation success = publish-ready. But `cargo check` only verifies compilation — it doesn't guarantee `Cargo.lock` is up to date with `Cargo.toml`. The publish workflow uses `cargo publish --dry-run` which DOES check `Cargo.lock`, exposing the gap only at runtime.

---

### Root Cause #2: Using detached-via-iteration HEAD was blindsided by tag creation

**Symptom:** Tag was created in detached HEAD state, remote push reported "up-to-date" repeatedly.

**Root cause:** Run-book step "Tag with `git tag v0.6.0 -m 'msg' and push" was insufficient. No verification that tag object points to the COMMIT, not the loose object.

**Fix in v0.6.0 workflow:**
- Added verification: `git cat-file -p v0.6.0 | head -n 10` to check tag points to HEAD
- Initialize force-push flow: `git push origin :refs/tags/v0.6.0 && sleep 2 && git push origin v0.6.0`
- No longer relying on detached HEAD tag tracking

**Why I made the mistake:** I trusted the local tag creation command to implicitly associate with HEAD. But `git tag` without a `-f` flag on sparsely checked-out/finite HEAD can still create a loose tag that doesn't have a commit ref. This is a git subtlety I'd overlooked because most of my workflows avoid git tag in detached-ish states.

---

### Root Cause #3: Hard-coded test expectations for the OLD default

**Symptom:** Test `segment_config_partial_eq_different_fields` failed because it expected DurabilityPolicy::Throughput to be DIFFERENT from default, but now default = Throughput.

**Root cause:** The test was written in the state BEFORE the v0.6.0 flip, and I updated it with a `#[test] rename` but NOT the data expectation.

**Fix in v0.6.0 workflow:**
- After suite passes as-is, rename test FIRST, THEN run suite
- If assertions fail, they will fail on the data, not the method name
- This makes upstream test failures more obvious (assertion message > function rename)

**Why I made the mistake:** I ran `cargo test` AFTER making ALL code changes. This gave me a false signal that tests were passing — not realizing the test had an outdated assertion that wouldn't catch the behavior change.

### System Identification: NEXUS

**Observation:** During this session (v0.6.0 DurabilityPolicy flip), three distinct categories of failures occurred:
1. Publish workflow failure (Cargo.lock not synced)
2. Tag force-push confusion (detached HEAD tag creation)
3. Test assertion mismatch (hard-coded expectation for old default)

**Pattern:**
- All three failures stemmed from **not thoroughly verifying release artifacts BEFORE pushing**.
- In v0.5.7, similar gaps led to last-minute hotfixes.
- This suggests we have systematic blind spots in our release verification flow.

**Conjecture:**
The projectId produce "greedy" releases because we iterate quickly on text-only changes but short-circuit the "verify everything" gate. We trust:
- `cargo check passes` → We assume the package is buildable
- `git tag exists` → We assume the tag points to the commit
- `cargo test passes` → We assume all assertions are correct

But none of these guarantees the next runtime check (publish) will succeed.

**Correction:**
I should have run a "release-ready checkpoint" BEFORE the final commit:
```bash
release-checkpoint() {
    # 1. Check CRITICAL failures first
    ! grep -A2 '"segment-buffer"' Cargo.lock | grep -q '"version": "0\..*"' && exit 1

    # 2. Check publish workflow
    cargo publish --dry-run --features encryption >/dev/null 2>&1 || {
        echo "ERROR: cargo publish --dry-run failed" >&2
        exit 1
    }

    # 3. Check tag points to HEAD
    git cat-file -p $(git describe --tags) | grep -q "$(git rev-parse HEAD)" || {
        echo "ERROR: Tag does not point to HEAD" >&2
        exit 1
    }

    # 4. Full verification gate
    bash scripts/verify-gate.sh || exit 1

    echo "✅ All release checks pass — proceed to publish"
}
```
