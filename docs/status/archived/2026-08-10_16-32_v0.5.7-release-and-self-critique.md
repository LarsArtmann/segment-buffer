## e) WHAT WE SHOULD IMPROVE

### Process improvements

1. **Add a Cargo.lock sync check to the release runbook.** After step 3
   ("Bump Cargo.toml version"), add: "Run `cargo check` to sync Cargo.lock,
   then commit Cargo.lock alongside the version bump." Or better: add a
   `scripts/check-cargo-lock-version.sh` that asserts Cargo.lock's
   `segment-buffer` version matches `Cargo.toml`.

2. **Add `cargo publish --dry-run` as a release gate.** The runbook
   mentions it in the backfill section but not in the main runbook steps.
   It catches dirty-working-directory, missing readme, bad metadata, etc.

3. **Add a Cargo.lock version-sync check to `verify-gate.sh`.** A new gate:
   extract `version` from Cargo.toml, extract the `segment-buffer` version
   from Cargo.lock, assert equal. This would have caught the issue before
   the first push.

4. **Split status reports into their own commits.** Status snapshots are
   documentation artifacts, not code changes. They should be committed
   separately, not swept into feature commits.

5. **The release commit message should use the actual version number.**
   Obvious, but I literally typed `vX.Y.Z`. Using a heredoc template with
   the version interpolated would prevent this.

### Quality improvements

6. **The verify-gate.sh runs BEFORE the version bump but NOT AFTER.** The
   gate validates the old version's consistency, not the new release's. The
   runbook should call for a targeted re-check after the bump: at minimum
   `cargo check`, `check-html-root-url.sh`, `check-msrv.sh`, and
   `cargo publish --dry-run --features encryption`.

7. **The changelog-links gate is degraded locally (403 rate limit).** The
   v0.5.7 tag didn't exist when the gate ran locally, so the new CHANGELOG
   link couldn't be verified. CI runs with `GITHUB_TOKEN` so it works there,
   but locally the gate gives a false sense of validation.
